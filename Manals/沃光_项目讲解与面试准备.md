# 《沃光》项目讲解与面试准备

> 用途：写进简历前的“事实核对 + 讲解稿 + 面试题库”；所有技术细节均可指到具体文件/函数，面试追问时能说清“为什么这么做”。

## 一、一分钟项目介绍（背熟）

《沃光》是一款 Godot 4.5 的 2D 像素风平台跳跃游戏，玩法是“蔚蓝式精准平台跳跃 + 空洞骑士式房间探索”，没有主动攻击，靠跳跃、能力解锁和房间回访推进。

我用 **GDScript** 独立完成了玩家物理与状态机、房间按需加载、地图与战争迷雾、多槽位存档、对话/任务/挑战/竞速/成就等系统，并完成了 Android 实机适配与导出。

项目约 **188 个脚本、2.5 万行有效代码、63 个房间场景、26 个全局单例**，已经做出可玩的 Android 与 Windows 构建。

**30 秒版本：**

一个用 Godot 做的 2D 平台跳跃游戏，我独立做了玩家手感、房间流式加载、地图和存档；手感上做了土狼时间、跳跃缓冲、墙跳、冲刺、相机限制等细节。

## 三、如何搭建（环境复现步骤）

1. 安装 **Godot 4.5.1 Stable**（标准版，非 .NET）。
2. 克隆/拷贝项目到本地任意目录，用 Godot 的 **项目管理器 → 导入** 选择 `project.godot`。
3. 首次打开会自动导入资源（`.import` 文件会重新生成），等导入完成。
4. 运行主场景：`F5` 或“运行项目”。入口是 `Scenes/UI/Scenes/TitleScene.tscn`。
5. 导出：
   - Android：安装 Android Build Template + SDK/NDK，在“项目 → 导出”里选 Android 预设；当前包名 `com.banjiu.warmagametest`。
   - Windows：同样在“导出”里加 Windows 预设，生成 `exe + pck`。
6. 常用命令行（无界面跑测试/校验）：

```powershell
# 版本
& 'D:\Tools\GameTools\GODOT\Godot_v4.5.1-stable_win64_console.exe' --version

# 无界面导入（首次或 CI）
& 'D:\Tools\GameTools\GODOT\Godot_v4.5.1-stable_win64_console.exe' --headless --path . --import

# 跑 GUT 单测（先建 tests/）
& '...\Godot_v4.5.1-stable_win64_console.exe' --headless --path . -s addons/gut/gut_cmdln.gd -gdir=res://tests -gexit
```

## 四、整体架构（面试重点）

### 4.1 运行流程

```text
TitleScene（标题）
   │ SceneManager.switch_scene() + FadeManager：黑屏三段式（淡出→保持→淡入），切场锁防重入
   ▼
SaveSelectScene（选存档）──► SceneManager.start_game_from_save(slot)
   ▼
MainGameScene
 ├─ RoomManager     按需加载：当前房间 + 相邻房间常驻，远处 queue_free
 ├─ Player          CharacterBody2D + 19 个状态 + 约 40 个职责服务（RefCounted）
 ├─ MapManager      房间布局 → 生成地图贴图；战争迷雾 Reveal Image；烘焙缓存
 ├─ DoorManager     门按 door_id 注册配对，传送时找另一扇门
 ├─ TeleportManager 传送阵激活与坐标
 ├─ SaveManager     user://saves/save_N.dat（JSON，tmp 原子替换 + 1.5s 合并窗口）
 ├─ EventBus        能力解锁等跨系统信号
 ├─ Global          玩家数值/能力/设置/存档序列化门面
 ├─ TaskManager     NPC 对话计数、任务标记
 ├─ AchievementManager / AchievementToast  成就与右下角提示（独立于存档）
 └─ AudioManager / CameraShakeManager / FadeManager / TimerControlManager / LightingManager / ...
```

### 4.2 设计取舍（这是面试加分点）

- **为什么用 Autoload**：单机游戏、单人开发，全局单例最直接；代价是耦合高、测试难。现在有 26 个，确实偏多。
- **为什么 Player 拆服务**：`Player.gd` 曾经太大，按“状态机 / 空中能力 / 移动 / 伤害 / 死亡 / 门传送 / 相机桥接”拆成 `RefCounted` 静态服务，`Player.gd` 只保留节点引用、导出参数和状态分发。
- **为什么用 Resource 配数据**：`ChallengeConfig`、`RaceStageConfig`、`AchievementCatalog`、`RoomLayoutData` 都是 `.tres`，方便 Inspector 调参和热改。
- **为什么用 EventBus**：能力解锁、竞速最佳成绩等跨系统事件，用信号解耦。

## 五、核心系统逐一说清楚（面试可深挖）

### 5.1 玩家移动与状态机

**做了什么**

- `Player` 是 `CharacterBody2D`，状态枚举 **19 个**：IDLE / MOVE / RUN / JUMP / DOWN / DASH / GLIDE / HURT / DIE / SLEEP / LOOKUP / LOOKDOWN / INTERACTIVE / RIDECART / WALLGRIP / WALLJUMP / SUPERDASHSTART / SUPERDASH / BACKSTEP。
- `PlayerStateFlowService.handle_state()` 用 `match` 按状态分发；各状态实现放在 `PlayerMovementService`、`PlayerAirAbilityService`、`PlayerGlideStateService` 等。
- 手感细节（都能在 `Player.gd` 导出参数里看到）：
  - **土狼时间** `coyote_time = 0.1s`：离开平台后短暂仍可跳。
  - **跳跃缓冲** `jump_buffer_time = 0.12s`：落地前提前按跳，落地立刻跳。
  - **可变跳跃高度**：按住跳跃 `max_jump_hold_time=0.2s` 内持续加 `jump_hold_boost`，松开即停止。
  - **边缘修正** `PlayerEdgeCorrectionService`：起跳/冲刺贴边时，逐像素探测并“抬上台阶”，避免轻微碰角直接打断动作。
  - **墙跳逃逸缓冲** `wall_jump_escape_buffer_time`：离墙后短时间内仍可墙跳，解决“双墙误挂”问题。
  - **跑步加速/衰减**、**跑出边缘**、**跑跳加成**、**撞墙反弹**。
- **帧率一致性**：`_physics_process` 里 `fixed_delta = min(delta, MAX_FRAME_TIME)`，加速度类参数通过 `get_accel_step_scale() = 60 * delta` 换算成“每秒”，保证不同步长手感一致。

**为什么这么做**

- 平台跳跃的“手感”来自大量小参数；土狼时间 + 跳跃缓冲是公认的“宽容错”技巧。
- 边缘修正把“擦边”从失败变成成功，显著降低挫败感。
- 固定 delta 上限 + 每步缩放，避免掉帧时角色“瞬移/加速”。

### 5.2 能力系统（9 个能力）

`Global.unlocked_abilities` 保存 9 个布尔：`dash / double_jump / glide / black_dash / wall_grip / super_dash / backstep / vertical_dash / map`。

- 解锁入口：NPC 对话（`Master` 一次授予大部分能力，`AerialRollMaster` 授予二段跳）、道具、调试。
- 解锁后通过 `EventBus` 信号广播，Player、AchievementManager 等订阅。
- 未解锁时对应输入无效（如 `try_dash` 先判断 `dash_unlocked`）。

### 5.3 房间系统与按需加载

- 每个房间是一个 `.tscn`，根节点 `Room.gd` 有 `room_id`、`room_bounds`、`adjacent_rooms`、`room_bgm_stream`、`room_color`。
- `RoomManager`：
  - `load_room()`：确保目标房间实例化 → `unload_distant_rooms()` 卸载非当前/非相邻房间 → 切 BGM、写 CanvasModulate、更新相机限制。
  - `_instantiate_room()`：首次 `load(scene_path)` 后缓存 `PackedScene`，之后只 `instantiate()`。
  - 卸载用 `queue_free()`，并清掉 `PackedScene` 缓存。
- `Door`：门按 `door_id` 成对注册；传送时黑屏 → `load_room(目标)` → 找另一扇门 → 把玩家放到对应位置 → 追镜/居中相机 → 淡入。
- 这是类银河恶魔城最典型的“房间流式加载”方案：**当前 + 相邻常驻，远处释放**。

### 5.4 地图与战争迷雾

- `RoomLayoutData` 是**唯一权威布局**：房间世界偏移 `room_positions`、房间边界 `room_bounds_rects`、门清单 `room_doors`、地图比例 `world_units_per_map_pixel = 16`、地形配色表。
- `MapManager` 用房间的 `TileMapLayer.get_used_cells()` 收集“地面横条（run）”，画到一张 `Image` 上生成整张地图贴图；门连线只画“玩家实际走过的门对”。
- 战争迷雾：`Image` 遮罩 + 玩家位置画圆；`reveal_step_world = 40px` 节流，距离不足不重绘。
- 性能优化：把“烘焙结果”存进存档（`map_baked`），读档后开图不再 `instantiate` 每个房间场景——这是“第一次开图卡顿”的针对性优化。
- `MapUI`：Shader `MapReveal.gdshader` 做迷雾显示；支持缩放/拖拽/双指缩放、房间名、任务标记。

### 5.5 存档系统

- `SaveManager`：`user://saves/save_N.dat`，JSON；先写 `.tmp` 再 `rename` 原子替换，失败回退直写。
- **合并窗口**：`request_auto_save()` 1.5 秒内多次请求只写一次盘，避免“拾取金币/对话当帧写盘”卡顿。
- `Global.get_save_data()` 汇总：玩家数值、能力、Boss/道具、检查点、NPC 对话、挑战/竞速记录、开关状态、地图已访问/迷雾/烘焙、传送阵。
- 成就单独存 `user://achievements.cfg`，删档不影响成就。

面试可以主动说局限：没有 schema 版本迁移、没有 checksum、没有 `.bak`；存档约 380 KB，其中 92% 是地图烘焙数据，gzip 可压到 53 KB——这是下一步优化点。

### 5.6 挑战 / 竞速 / 成就

- `ChallengeController`：JumpBox 挑战，普通触发 1 分、完美触发 2 分；无尽模式连续完美额外 +1/次，封顶 9 分。
- `RaceController`：5 个赛段，按检查点顺序 `next_expected_index` 判定，记录最佳时间与达成日期；无尽模式积分榜保留历史前三。
- `AchievementManager`：14 个成就；能力类成就直接订阅 `EventBus` 的能力解锁信号；`unlock()` 幂等。
- `AchievementToast`：独立 autoload，任何场景都能弹“成就达成/存档已更新”。

### 5.7 相机

- Phantom Camera 负责基础跟随；`PlayerCameraController`（约 1,400 行）在它之上做：
  - **房间限制框**：进房时按 `room_bounds + margin` 写入 `limit_*`。
  - **CameraLimitZone**：每帧按“玩家是否在矩形内”判定（不依赖物理信号，传送/读档也能立刻判定），限制框平滑收敛、进/出死区防止边界抖动。
  - **CameraFocusBeacon**：让相机“抢夺焦点”看向剧情点，带最大偏移和平滑系数。
  - **观察偏移**：抬头/低头时相机偏移；**奔跑前视**：高速时给前方偏移。
  - **传送追镜**：门传送后短暂放开限制、追到玩家再收回。

## 六、数据处理与性能优化清单（面试常问“你做过什么优化”）

| # | 优化 | 问题 | 手段 | 效果/指标 |
|---:|---|---|---|---|
| 1 | 房间按需加载 | 全图常驻内存/加载慢 | 当前+相邻常驻，远处 `queue_free`；`PackedScene` 缓存 | 内存与首次进入时间随房间数线性可控 |
| 2 | 自动存档合并 | 拾币/对话当帧写 380KB 卡顿 | 1.5s 合并窗口 + tmp 原子替换 | 高频操作不再掉帧 |
| 3 | 地图烘焙缓存 | 读档后首次开图要 instantiate 所有去过房间 | 烘焙结果随存档保存，开图直接命中 | 开图不再逐个加载场景 |
| 4 | 迷雾重绘节流 | 每帧重绘整张遮罩 | 移动距离小于 `reveal_step_world` 跳过 | 大幅减少 CPU/纹理上传 |
| 5 | 残影对象池 | 冲刺/二段跳反复 `instantiate/free` GC 抖动 | `AfterimagePool` 预热复用 | 减少瞬时分配抖动 |
| 6 | 音效池 + 优先级 | 同时触发大量 SFX 抢占/爆音 | 12 个池化播放器 + 每优先级上限 + 抢占最低优先级 | 稳定混音、不爆音 |
| 7 | 粒子分级 | 低端机/手机发热 | 特效等级 LOW~ULTRA → 粒子 amount 倍率；低档封 60fps | 低端机可玩 |
| 8 | 物理插值 | 60Hz 物理在高刷屏上视觉抖动 | `physics_interpolation=true` | 高刷屏平滑 |
| 9 | 像素整数缩放 | 非整数缩放糊 | `viewport + integer`；手机切 fractional | 像素清晰 |
| 10 | 编辑器文本扫描 | 实例化 20+ 房间拖慢编辑器 | `RoomScanner` 只解析 `.tscn` 文本头几行 | 扫描布局秒级完成 |
| 11 | 背景纯函数摆放 | 视差背景换格时错位闪帧 | `GroundParallaxController` 用“相机坐标的纯函数”算格点，去掉历史状态 | 消除错位帧 |

回答“怎么发现的”：用 **print/日志 + 分阶段计时 + 手机实机测试** 发现的；不是凭空优化。可以坦白“还没做正式 profiler 采样”。

## 七、我遇到并解决的问题（STAR 模板，面试必背）

### 案例 1：双墙误挂 / 超级冲刺方向错乱

- **S**：窄缝两墙间墙跳，会“挂到对面墙”，攀墙方向反了；超级冲刺中按冲刺，方向被锁成右边。
- **T**：修复但不破坏合法操作（两墙间切换攀墙、滑翔中重新抓墙）。
- **A**：把 `wall_direction`（当前位置真实射线命中的墙）与 `wall_grip_direction`（本次墙跳/攀墙锁定的墙）**分离**；空中重新附着只读“当前射线结果”；超级冲刺的 `SUPERDASH→DASH` 切换点重新计算冲刺方向，减速阶段复用普通空中输入入口。
- **R**：两个问题都修复并验证；复盘写进 `Manals/双墙冲刺临时BUG_2026-05-30.md`。
- **可延伸**：这是“**状态之间共享变量语义不清**”导致的典型 bug；教训是“一个变量只表达一件事”。

### 案例 2：首次开图卡顿

- **S**：读档后第一次打开地图明显卡顿。
- **T**：定位原因并优化。
- **A**：发现 `bake_pending_visited_rooms()` 会对“去过但本次会话未烘焙”的房间逐个 `load + instantiate` 整个场景；改为**把烘焙结果随存档保存**，读档后直接命中。
- **R**：第一次开图不再做场景实例化；代价是存档变大（380KB），后续可用压缩/只存已访问房间继续优化。

### 案例 3：UI 输入锁死（按钮永久点不动）

- **S**：UI 页面切换后偶发按钮全部无响应。
- **T**：找出根因并统一收口。
- **A**：根因是各页面各自 `await` 一次性信号，某次信号丢失导致锁永不释放；抽出 `UIScene` 基类，统一“锁输入 → 播动效 → 等动效总线空闲 → 解锁”，并加**兜底超时**。
- **R**：4 个页面 25 处重复代码收敛到一处，输入锁死问题消失。

### 案例 4：手机画面只占一小块

- **S**：手机分辨率（如 2400×1080）不是 1280×720 的整数倍，`integer` 缩放向下取整成 1 倍。
- **T**：手机端像素清晰但不黑边。
- **A**：提供三档适配：默认像素完美 / **等比放大（fractional + keep）** / 拉伸填满；启动时读 `user://display_settings.cfg`。
- **R**：手机端可铺满且保持比例。

## 九、面试题库与参考答案

回答原则：先给结论，再说“为什么”，最后说“局限/改进”。

### A. 项目与架构类

**Q1：简单介绍一下这个项目。**
短答：见第一节 30 秒版本。展开：玩法（蔚蓝式平台跳跃 + 空洞骑士式房间探索，无主动攻击）、技术栈（Godot 4.5 / GDScript / GL Compatibility / 1280×720 像素风）、规模（188 脚本、2.5 万行、63 房间、26 autoload）、成绩（Android + Windows 可玩构建）。

**Q2：为什么选 Godot 而不是 Unity？**
短答：2D 原生、GDScript 上手快、导出 Android 轻量、开源免费；单人项目开发效率高。
展开：Godot 的 2D 坐标/像素对齐更直接，TileMapLayer、CharacterBody2D、场景实例化适合“房间制”关卡；代价是生态和招聘市场需求不如 Unity/UE。

**Q3：你的架构是怎么分层的？**
短答：`Manager（跨场景生命周期）+ Service（Player 内部职责）+ Resource（配置数据）+ EventBus（跨系统信号）`。
展开：Manager 是 autoload；Player 把状态细节拆到 `RefCounted` 静态服务；配置用 `.tres`；跨系统用信号解耦。

**Q4：为什么有 26 个 Autoload？不觉得多吗？**
短答：单人开发用全局单例最直接；我现在意识到偏多，会按“是否跨场景 + 是否全局唯一”收敛。
展开：可合并的候选（TaskManager 并入 Global/Quest、ScenePaths 改为常量类），但重写风险高，当前优先做内容。

**Q5：`Player.gd` 为什么这么大？**
短答：它是状态机的“门面 + 参数中心”，细节已经拆到约 40 个服务；但导出参数和状态分发仍在主类。
展开：下一步可以把导出参数按“移动/跳跃/冲刺/墙”分组到 Resource，主类只留状态分发。

**Q6：如果让你重做，你会怎么做？**
短答：保留玩法与手感，改三处：①存档 schema 版本化 + 压缩；②把 `Global` 的“设置/存档/玩家数据”拆开；③补自动化测试（GUT）。
展开：不重写 Player，因为手感是资产；用“小步重构 + 测试保护”替代大重写。

### B. 玩家物理与状态机

**Q7：土狼时间和跳跃缓冲是什么？为什么需要？**
短答：土狼时间 = 离开平台后 0.1s 内仍可跳；跳跃缓冲 = 落地前 0.12s 内按跳，落地立刻执行。都是“宽容错”，让玩家觉得“操作响应好”。
展开：实现用 Timer；`update_coyote_time()` 只在“刚从地面离开、下落中、非跳跃”时激活。

**Q8：怎么保证不同帧率下手感一致？**
短答：物理固定 60Hz；`_physics_process` 里 `fixed_delta = min(delta, 1/30)`；加速度类参数用 `60 * delta` 换算。开 `physics_interpolation` 让渲染平滑。

**Q9：可变跳跃高度怎么实现？**
短答：按住跳跃在 `max_jump_hold_time` 内持续加 `jump_hold_boost` 到垂直速度；松开即停止；再配合最大下落速度。

**Q10：墙跳/墙钳（WALLGRIP）怎么判断墙？**
短答：用射线/`is_on_wall()` 检测，区分“当前真实接触墙 `wall_direction`”和“本次锁定墙 `wall_grip_direction`”，并加“离墙逃逸缓冲”防止刚墙跳又立刻吸附。

**Q11：冲刺/超级冲刺/后撤步的优先级怎么处理？**
短答：输入先判“后撤步（地面+下+冲刺）”→“垂直冲刺（按住上/下且已解锁）”→“水平冲刺”；超级冲刺是长按蓄力后进入，减速阶段复用普通空中输入。

**Q12：玩家和移动平台怎么同步？**
短答：不依赖物理引擎自动携带；`Platform` 暴露 `get_platform_velocity()`，Player 每帧主动叠加平台速度（蔚蓝风格），避免“站在平台上被甩下去/受伤时与平台碰撞”。

**Q13：相机是怎么做的？**
短答：Phantom Camera 基础跟随 + 自写 `PlayerCameraController`：房间限制框、CameraLimitZone（按矩形判定，不依赖物理信号）、FocusBeacon 焦点抢夺、观察/奔跑偏移、传送追镜。
可展开：进/出死区防止边界抖动；限制框用速度/加速度平滑收敛，避免硬切。

### C. 房间、地图、存档

**Q14：房间是怎么加载的？为什么这么设计？**
短答：每个房间独立 `.tscn`；当前 + 相邻常驻，远处 `queue_free`；`PackedScene` 缓存；门传送时黑屏后切换。
展开：这是类银河恶魔城常用方案，兼顾内存与“过门无缝”；局限是相邻判定依赖 `adjacent_rooms` 手工维护，容易漏。

**Q15：地图是怎么生成的？**
短答：以 `RoomLayoutData` 为唯一权威（房间偏移/边界/比例 16px/配色），扫描每个房间 TileMapLayer 的地面格生成“横条”，按世界→像素比例画到 Image 上；迷雾用单独遮罩。
展开：门连线只画实际走过的门对；Shader 负责迷雾显示。

**Q16：地图第一次打开卡顿，你怎么优化的？**
短答：见案例 2：把烘焙结果存进存档，读档后直接命中，不再实例化房间场景。

**Q17：存档怎么做的？**
短答：JSON 写到 `user://saves/save_N.dat`；先写 `.tmp` 再 rename 原子替换；自动存档 1.5s 合并窗口；成就单独文件。
局限：无版本迁移、无 checksum、无备份；380KB 中 92% 是地图烘焙，可 gzip 到 53KB。

**Q18：如果存档损坏/版本升级怎么办？**
短答：现在只是解析失败返回空；正确做法是 `schema_version + 迁移链 + SHA-256 + .bak`，这是我知道的下一步。

### D. 性能与优化

**Q19：你做过哪些性能优化？怎么衡量的？**
短答：见第六节 11 条；衡量方式主要是“高频操作掉帧复现 + 分阶段计时 + 手机实机测试”。
局限：还没做正式 profiler（CPU/GPU 分帧）采样，下一步会用 Godot Profiler 给出 p95 数据。

**Q20：内存怎么控制的？**
短答：房间按需加载 + 卸载、PackedScene 缓存、残影对象池、音效池；纹理多为 512×288 以内，主要是 2D。

**Q21：对象池解决了什么问题？**
短答：冲刺/二段跳残影频繁创建/销毁会导致 GC/分配抖动；`AfterimagePool` 启动时预热，用完归还复用。

### E. 工程与测试

**Q22：有没有写测试？**
短答：诚实说“目前没有自动化测试，是我现在的短板”；已装 GUT，计划补 5 个 smoke test（启动、存档读档、门传送、房间切换、门配对）。

**Q23：怎么调试的？**

**Q23b：Git 怎么用的？**
