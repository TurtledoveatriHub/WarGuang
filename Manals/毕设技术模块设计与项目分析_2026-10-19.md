### 1.2 运行时架构

```text
TitleScene / SaveSelectScene
        │  SceneManager + FadeManager（切场锁、黑屏三段式）
        ▼
MainGameScene
 ├─ RoomManager        按需加载 current + adjacent；Door 触发切房
 ├─ Player             19 状态枚举 + 约 40 个职责服务
 ├─ MapManager         RoomLayoutData / 战争迷雾 / 烘焙地图 / 门连线
 ├─ DoorManager        门注册与配对
 ├─ TeleportManager    传送阵激活与坐标
 ├─ SaveManager        user://saves/save_N.dat（JSON + tmp 原子替换）
 ├─ EventBus / Global  能力解锁、进度、玩家数值
 ├─ TaskManager       NPC 对话计数、任务标记
 ├─ AchievementManager 成就（独立于存档）
 └─ DialogueManager / PhantomCamera / Audio / UI / Mobile HUD
```

这是一套“**Manager + Service + EventBus + Resource**”的混合架构：管理器负责跨场景生命周期，Player 把物理/状态细节拆到服务层，数据配置放在 `.tres` / `.dialogue` 里。方向是对的，但边界还没有完全收干净。

### 1.7 存档与性能（实测）

现有两份存档样本：

| 项目 | 数值 |
|---|---:|
| `save_0.dat` | 379.3 KB |
| 其中 `map_baked` | 351.5 KB |
| `map_baked` 内房间数 | 63 |
| `map_baked` 内地面 run 数 | 12,520 条 |
| `map_reveal_mask`（Base64 PNG） | 25.9 KB |
| 整份 JSON 经 gzip | 53.5 KB（约 7.3× 压缩） |
| 存档键数量 | 41 |

也就是说：**一份 2D 存档里 92% 是地图烘焙数据**。现有代码把 `_gen_rooms` 全量写入 `map_baked`；如果只去过 4 个房间却存了 63 个房间的 12,520 条地面 run，就有明显的“增量/压缩”空间。再叠加“金币变动也触发自动存档”，380 KB 的重复写盘并不划算。

### 1.8 视觉与 UI（基于现有截图/素材的有限评估）

标题界面截图（1280×720）整体是暖橙渐变 + 像素标题卡 + 右侧箭头按钮，风格统一、角色可爱、可读性不错。主要问题：

1. **构图偏右重左轻**：标题卡在左上，菜单整体贴右，中间大片空；如果这是刻意留白，建议加一层低对比度视差/粒子，避免“空”。
2. **层级不齐**：主菜单按钮大，左下“关于作者/游戏公告”很小，视觉权重差距过大；建议统一 16px 网格与内边距。
3. **素材分辨率不统一**：背景多为 512×288，标题卡 144×128，UI 集也是 512×288；在 1280×720 下靠缩放，边缘容易糊。像素风应固定整数倍缩放/导入预设。
4. **旧 UI 素材残留**：`旧版UI.png`、`旧版UI2.png`、`场景UI集.png` 等仍在，容易误用；建议归档到 `Assets/Textures/_Legacy/` 并在导入预设里统一过滤。
5. **交互反馈**：现有按钮有按下/悬停纹理，但标题菜单的键盘/手柄焦点态、选中态、页面切换动效还可以更明确。

> 我只看了标题截图和少量 UI/背景素材，没有逐房间实机巡查；这一节的视觉判断是“方向性建议”，不是最终美术结论。

## 2. 分析评价与优化建议

### 2.1 做得好的地方

- **手感参数非常认真**：土狼时间、跳跃缓冲、边缘修正、墙跳逃逸、冲刺转向、Hit Stop、相机观察偏移，这些不是“能跑就行”的原型会做的。
- **性能有工程意识**：房间按需加载、远处卸载、地图烘焙缓存、对象池、粒子分级、物理插值、自动存档合并，说明作者想过“上线后会不会卡”。
- **数据驱动程度高**：1,306 个 `@export`、`ChallengeConfig`/`RaceStageConfig`/`AchievementCatalog`/`RoomLayoutData`，关卡和挑战可以在 Inspector 里调。
- **文档与复盘**：`Manals/` 里有房间 ID 手册、UI 过渡计划、双墙冲刺 Bug 复盘；这在学生项目里很少见。
- **多端与可访问性**：移动端 HUD、按键重映射、画面填充模式、特效等级、三语本地化，都是“产品化”思维。

### 2.2 主要风险（按优先级）

| 优先级 | 问题 | 证据 | 影响 | 建议 |
|---|---|---|---|---|
| P0 | 门/房间/相邻数据不同源 | 1 处自指、6 条缓存位置过期、4 条门元数据缺失、6/8 相邻不一致 | 加房间时容易“门连不过去/地图少一条线”，且很难排查 | 先写一个**只读校验器**，把 `ScenePaths`、场景、`RoomLayoutData`、Door 图四方比对；这是施工工具，不是“修 bug” |
| P0 | 没有自动化测试/CI | 无 `tests/`、无 `.github/workflows` | 论文实验无法复现，重构不敢动 | GUT + 5 个 smoke test + GitHub Actions headless |
| P0 | 存档 schema 无迁移/校验 | `SAVE_VERSION=1` 定义但未使用；JSON 解析失败返回 `{}` | 加字段/改字段后旧档可能静默损坏 | `schema_version` + 迁移链 + SHA-256 + `.bak` |
| P1 | 存档写盘热点 | 12 处直接 `save_game`；380 KB/次 | 拾取/对话/解锁时掉帧 | 全部走 `request_auto_save`，并压缩/增量 |
| P1 | `Global` 过大 | 819 行、40+ 字段，混合玩家数值/设置/存档/时长 | 改一处牵连多系统 | 先加 `SaveSchema`/`SettingsService` 门面，不急着拆 |
| P1 | 反射与日志 | 439 `has_method`、200 `print` | 静态分析困难、发布版噪声 | 引入 `Log` 分级；关键接口用基类/组，不一次性替换 |
| P1 | 仓库臃肿 | `android/build` 1.04 GB、630 个跟踪文件、`.git` 432 MB | clone/备份/提交慢，易冲突 | `.gitignore` 加 `android/build/`、`recovery/`、`__pycache__/`；大文件 LFS；从索引移除构建产物 |
| P2 | 内容深度不足 | 22 个 <10 KB 房间、7 个金币、3 个可破坏墙 | 全图体验断裂，实验样本少 | 先做 6–8 房间 vertical slice，不要平均用力 |
| P2 | 视觉规格不统一 | 512×288 背景、144×128 标题、旧 UI 素材 | 缩放糊、风格漂移 | 统一 16px 网格/导入预设，旧素材归档 |
| P2 | 文档与代码同步 | `房间系统手册` 仍写 26 个房间，实际 63 | 新人/未来的你会被误导 | 把手册里的“当前登记状态”改为自动生成 |

### 2.3 现在不要做的事

- **不要重写 `Player.gd` / `Global.gd`**。它们很大，但当前能跑；毕设时间应该花在“可验证的技术贡献”上，而不是高风险重构。
- **不要自动 `gdformat` 全项目**。36k 行会制造巨大 diff，评审和回滚都痛苦。
- **不要升级 Phantom Camera / Dialogue Manager**。0.9.3.1 / 3.10.2 已经深度接入，换版本可能破坏相机和对话。
- **不要现在接战斗、Boss、联网、强化学习**。内容与数据都不够，投入产出比低。
- **不要把“物理可达性”作为唯一方案**。它最容易做成“看起来很酷但跑不完”的模块，必须有 authored graph 兜底。

## 4. 毕设技术模块设计

### 4.1 设计原则

1. **加法优先，不改核心手感**：新模块先以“只读观察/编辑器工具”接入，确认有价值再进运行时。
2. **数据与表现分离**：关卡图、遥测事件、存档 schema 都先定义数据契约，再接 UI。
3. **可度量**：每个模块必须有“before/after”指标，否则论文没法写。
4. **可回退**：用 feature flag / 独立 autoload / 独立目录，出问题能一键关。
5. **不与现有系统抢职责**：遥测订阅 `EventBus`，不侵入 Player；关卡图读场景，不改场景；存档模块包在 `SaveManager` 外层。

### 4.2 候选模块总表（按“性价比”排序）

> 难度 1–5（5 最难）；论文价值 1–5（5 最强）；工期按 1 人全职估算，含测试与文档。

| 排序 | ID | 模块 | 类型 | 难度 | 论文价值 | 工期 | 玩法风险 | 依赖 |
|---:|---|---|---|---:|---:|---|---|---|
| 1 | **A1** | 房间图建模与能力门禁求解 | 算法 / 图论 | 3 | 5 | 2–3 周 | 低 | 无 |
| 2 | **B1** | 玩家行为遥测与难度分析 | 大数据 / 统计 | 3 | 5 | 3–4 周 | 低 | 无 |

**分梯队理解：**

- **第一梯队（建议主线）**：A1、B1、B2。三者互相支撑：A1 产出关卡图，B1 产出真实游玩数据，B2 保证改东西不坏。
- **第二梯队（拔高）**：A2。做好了是论文最亮的算法章；做不好会拖垮进度，所以必须“A1 先兜底、A2 增量做”。

- **第四梯队（当前不建议）**：E1。没有战斗和 Boss 内容，AI 模块容易变成“演示”。

### 4.3 模块 A1：房间图建模与能力门禁求解（首推）

**解决什么问题**

现在的房间关系是“隐式”的：`ScenePaths` 知道路径，`RoomLayoutData` 知道位置，`Door` 知道 `door_id/target_room_id`，`adjacent_rooms` 又存了一份。它们之间没有一张**唯一的、可计算的图**。所以：

- 新增房间要改 5 个地方（文档自己也写了）；
- 门对不齐、目标写错、相邻漏写，只能靠人眼看；
- 无法回答“按当前能力，哪些房间可达”“这个能力放在这里会不会造成 softlock”“最短通关顺序是什么”。

**数据模型**

```text
LevelGraph
├─ nodes: room_id -> RoomNode { scene_path, bounds, biome, tags }
├─ edges: Array[DoorEdge]
│    DoorEdge { door_id, from_room, to_room, one_way,
│                required_ability_mask, required_item_ids,
│                reward_ability, reward_item, challenge_id }
└─ start_room, goal_rooms
```

能力用 9 位 bitmask 表示：`dash / double_jump / glide / black_dash / wall_grip / super_dash / backstep / vertical_dash / map`。这与 `Global.unlocked_abilities` 完全对齐，不需要改存档。

**构建方式**

1. 读 `ScenePaths.ROOM_PATHS` 和 `RoomLayoutData`，得到 63 个节点。
2. 扫描每个房间的 `Doors` 容器，读 `door_id/target_room_id`，得到 152 条有向边。
3. 用 `door_id` 配对，校验双向一致性；不一致的边标红。
4. 能力门禁先支持两种来源：
   - 手动：在 `Door` 或新 `AbilityGate` 节点上加 `@export var required_abilities: Array[StringName]`；
   - 自动推断：`DestructibleWall`、`Switch`/`MechanismGate`、`JumpBox` 挑战区、高台落差等，作为“候选门禁”提示，不自动定死。
5. 输出 `LevelGraph.tres`（编辑器生成，运行时只读）。

**求解算法**

```text
BFS over (room_id, ability_mask)
  state = (room, mask)
  for edge in graph.edges[room]:
      if edge.required_mask & ~mask != 0: continue
      next_mask = mask | edge.reward_mask
      if (edge.to, next_mask) not visited:
          push
```

在此基础上加：

- **状态支配剪枝**：同一房间若已访问过“能力集合是当前集合超集”的状态，则当前状态可剪枝；物品用 bitmask/计数向量表示，维护 Pareto 前沿，避免 `(room, mask)` 状态爆炸。这是把“BFS”提升为“带支配关系的最优可达性搜索”的关键。
- **最小能力顺序**：先由“获得能力 X 需要先到哪些房间”构造能力依赖图，再做拓扑排序；若依赖图有环，说明存在“鸡生蛋”式门禁，直接报错。
- **Softlock 检测**：从目标房间反向搜索，找出“只能进、不能出”的单向边/房间；再检查这些区域是否包含通关所需物品，标记为潜在死锁。
- **序列破坏**：对比“设计顺序”和“实际可达顺序”，找出玩家可以提前拿到的能力。
- **关键路径 / 枢纽房间**：用 betweenness centrality 找“必经房间”，为地图引导和检查点布置提供依据。
- **可达率**：按能力阶段统计可达房间/收集品比例，直接作为关卡设计指标。

**接入点**

- 新增 `Scripts/Research/LevelGraph/`（或 `addons/level_graph/`），不改现有 `RoomManager`。
- 编辑器工具按钮：`扫描房间图`、`校验`、`求解`、`导出 GraphViz`。
- 运行时只读：`MapUI` 可叠加“当前可达/不可达”颜色；debug overlay 显示状态。
- 论文图表：房间图、能力门禁矩阵、解锁顺序、softlock 案例。

**评价指标**

- 63 节点 / 76 对门 / 152 条边的构图耗时（目标 < 200 ms）。
- 求解耗时（目标 < 10 ms）。
- 注入 20 个数据错误（改 door_id、target、adjacent、required_abilities），召回率/误报率。
- 与人工设计的能力顺序对比：是否一致、是否发现“可跳过”的路径。
- 代码覆盖率：图构建/求解/校验三条链路。

**难度与风险**：3/5；2–3 周；低风险。**这是最推荐先做的模块**，因为它不碰玩法，却能立刻提升项目的数据质量，并且是论文里最像“算法”的一章。

### 4.4 模块 B1：玩家行为遥测与难度分析（大数据主线）

**解决什么问题**

现在项目只有“最佳时间/无尽积分/成就”这类结果数据，没有“过程数据”。所以无法回答：

- 玩家在哪一房间死得最多？是哪个平台/哪段冲刺？
- 某个检查点是不是太远？某段挑战的失败是“难度”还是“操作不明确”？
- 新加的引导有没有降低流失？能力解锁顺序是否符合预期？

**事件模型**

| 事件 | 关键字段 | 用途 |
|---|---|---|
| `session_start/end` | session_id, build, slot_hash, locale, device | 会话、版本、设备分层 |
| `room_enter/exit` | room_id, world_pos, ability_mask, play_time | 房间停留、路径、卡点 |
| `death` | room_id, world_pos, cause, attempt_index | 死亡热力图、难度 |
| `checkpoint` | checkpoint_id, room_id, type | 检查点覆盖率 |
| `door_use` | door_id, from, to, duration | 门使用频率、连接热度 |
| `ability_unlock` | ability, source, room_id | 解锁顺序、引导效果 |
| `item_collect` | item_id, room_id | 收集率、漏拿点 |
| `challenge_start/end` | challenge_id, stage, result, duration, score | 挑战通过率、耗时分布 |
| `race_start/finish` | stage, laps, time, best | 竞速平衡 |
| `fps_sample` | p50/p95/p99, draw_calls, memory | 性能与体验相关性 |

公共字段：`event_id`、`session_id`、`build_version`、`timestamp_ms`、`play_time_ms`、`room_id`、`world_pos`（量化到 8px）、`ability_mask`。**不采集**用户名、系统路径、按键内容等隐私数据。

**架构**

```text
Game (GDScript)
  Telemetry autoload
    ├─ EventBus 订阅（只读）
    ├─ RingBuffer 512 条
    ├─ 每 30s / 切房 / 退出时 flush
    └─ user://telemetry/session_<id>.jsonl（可 gzip）

Offline pipeline (Python)
  JSONL -> pandas/polars 清洗 -> Parquet/SQLite
        -> 指标计算（KDE/聚类/生存分析）
        -> Streamlit dashboard + matplotlib 图表
```

**分析方法（这是“大数据”章节的核心）**

- **死亡热力图**：对死亡坐标做 Gaussian KDE，带宽 32–64px；按房间归一化，找“热点平台”。
- **卡点排名**：`choke_score = z(死亡率) + z(中位尝试时长) + z(退出率)`；输出 Top-10 房间/坐标。
- **难度指数**：`difficulty = 0.4*death_rate_norm + 0.3*time_norm + 0.2*retry_norm + 0.1*item_miss_norm`，权重可用 PCA/专家打分校准。
- **玩家聚类**：KMeans/DBSCAN（特征：死亡率、通关时长、能力使用频率、收集率）；用 silhouette 选 k。
- **生存分析**：对挑战阶段做 Kaplan–Meier 曲线，估计“第 N 次尝试通过概率”。
- **变点检测**：Page–Hinkley / CUSUM 找“某房间突然变难”的版本/段落。
- **A/B 测试**：检查点位置/提示频率两个版本，用 bootstrap 置信区间比较死亡率/完成时间。
- **序列模式**：房间访问序列的 n-gram / 马尔可夫链，找“反复绕路”的路径。

**数据量说明（要诚实）**

单人本地游玩的数据量不算“大数据”。论文里不要硬说 Hadoop，正确说法是“**游戏遥测数据采集—清洗—存储—分析—可视化流水线**”，并用两种数据源补足规模：

1. 10–20 名测试者的真实会话（每组 30–60 分钟）。
2. 自动化试玩机器人（B2）生成的合成轨迹（例如 1,000 局 × 5 分钟 × 60Hz 的位置采样 = 1,800 万帧），用于验证管线吞吐和热力图稳定性。

这样既有真实数据，又有规模，逻辑上站得住。

**评价指标**

- 数据完整性：事件丢失率、flush 成功率、崩溃恢复。
- 分析有效性：能否自动找出 3 个已知卡点；与人工标注的一致率。
- 性能：遥测对帧时间的影响（目标 p95 增加 < 0.3ms）。
- 体验：根据分析调整 1–2 个检查点/提示，比较调整前后的死亡率/完成时间（小样本用 bootstrap，不强行显著）。

**难度与风险**：3/5；3–4 周；低风险，但**依赖测试者**。如果找不到人，就用 B2 的机器人数据 + 你自己 3 个存档的游玩数据，先跑通管线。

### 4.5 模块 A2：平台跳跃物理可达性验证（高难度、高价值）

**解决什么问题**

A1 只能验证“门和图”的逻辑可达，不能验证“这段跳跃真的跳得过去”。A2 要回答：

- 每个金币/门/检查点，在当前能力下是否物理可达？
- 某个 gap 是否需要“像素级”操作？难度是否超出目标？
- 新增平台后，是否把某条路堵死/让某条路变得太简单？

**技术路线（建议分三期，不要一口吃成胖子）**

**一期：解析跳跃包络（1–1.5 周）**

- 从 `Player.gd` 的导出参数读出：`jump_velocity`、`gravity`、`max_fall_speed`、`base_move_speed`、`run_move_speed`、`double_jump_velocity`、`dash_speed`、`glide_*`。
- 用 projectile 公式计算“单跳/二段跳/冲刺”的最大水平距离与最大高度包络。
- 对每个平台的边缘采样点，判断目标平台是否落在包络内；输出“可能可达/不可能”。
- 这是保守近似，会**高估**可达性，但能快速筛掉明显不行的 gap。

**二期：动作原语 + 图搜索（2–3 周）**

- 从 `TileMapLayer.get_used_cells()` + `TileData.get_collision_polygons_count()` 提取实体碰撞；从 `Platform`/`IcePlatform`/`BreakablePlatform` 提取单向/可破坏平台；从 `JumpBox`/`UpdraftZone`/`WindValleyZone`/`PixelWaterSurface` 提取特殊运动区。
- 把“可站立表面”离散成采样点（每 8px 一个），构建 `SurfaceGraph`。
- 动作原语：走、跑、跳、二段跳、冲刺（8 向）、滑翔、墙跳、超级冲刺、跳板/弹簧、上升气流、水流。
- 用固定步长 1/60s 的简化运动模型模拟每条原语，碰撞用 `PhysicsDirectSpaceState2D` 或自建 AABB 查询；成功则加边。
- 对 `(surface, ability_mask)` 做 BFS/A*；输出可达表面、不可达目标、最短动作序列。

**三期：难度与鲁棒性（1–2 周）**

- 对每条边计算“安全裕度”：距离危险区的最短距离、时间窗口、需要的最少输入数。
- 用 RRT/随机扰动测试“边缘情况”，找“理论可达但人类几乎做不到”的 gap。
- 与 B1 的真实死亡热力图对比，校准模拟器（sim-to-game calibration）。

**评价指标**

- 对 10 段人工 replay 的可达性判定：precision/recall（目标 > 85%）。
- 单房间构图/求解耗时（目标 < 2s/房间）。
- 发现当前项目中“不可达金币/门”的数量（先人工复核）。
- 难度指标与玩家死亡率的相关性（Spearman ρ）。

**风险与缓解**

- 最大风险是**物理保真度**：Player 有大量特殊状态（墙跳、超级冲刺、矿车、环境风），完整复刻成本高。
- 缓解：A2 只做“离线验证器”，不改 Player；先用解析包络，再逐步加原语；只对 3–5 个代表性房间做高保真，其余房间用保守模型。
- 如果时间不够，论文可以写成“**混合式可达性验证：逻辑门禁图 + 物理包络**”，A1 是主贡献，A2 是增强，不会全盘皆输。

**难度与风险**：5/5；4–6 周；高风险。建议在 A1/B1 稳定后再启动。

### 4.6 模块 B2：自动化回归测试与试玩机器人

**为什么需要**

你接下来会不断加房间、改平台、调能力顺序。没有回归测试，每次改完只能“手动跑一遍”，论文实验也无法复现。

**测试内容**

| 层级 | 测什么 | 工具 |
|---|---|---|
| 单元 | `SaveCodec` 迁移/校验、`LevelGraph` 求解、地图坐标换算、输入重映射、挑战计分 | GUT |
| 集成 | 标题→存档→游戏、门传送、房间切换、对话开始/结束、死亡重生 | GUT + 场景测试 |
| 端到端 | 固定输入 replay 30–60s：不崩、不穿地、能切房、存档可回读 | GUT + `Input.parse_input_event` |

**试玩机器人**

- 录制：每个 physics tick 记录输入位掩码（左/右/跳/冲刺/交互）+ 随机种子。
- 回放：固定 `Engine.physics_ticks_per_second=60`，逐帧注入，状态哈希对比。
- 模糊测试：随机输入序列，奖励“新房间/新门/新收集品”覆盖（coverage-guided fuzzing）。
- 不变量：
  - 玩家位置在房间 bounds 内（允许门过渡窗口）；
  - 不穿地/不穿墙；
  - 生命值/金币/能力在合法范围；
  - `door_id` 配对始终完整；
  - 存档→读档→再存档，关键字段一致。

**CI**

```yaml
# .github/workflows/tests.yml（示意）
- uses: actions/checkout@v4
- name: Run GUT
  run: godot --headless --path . -s addons/gut/gut_cmdln.gd -gdir=res://tests -gexit
- uses: actions/upload-artifact@v4
  with:
    name: gut-results
    path: test_results.xml
```

**评价指标**：测试数量/覆盖率、CI 时长、注入 20 个 bug 的检出率、flaky rate。

**难度**：3/5；2–3 周；低风险。**建议与 A1 同期做**，因为 A1 的求解器最适合先写单元测试。

### 4.7 模块 C1：存档版本化 / 压缩 / 校验

**现状问题**

- `SAVE_VERSION=1` 但 `get_save_data` 里没有迁移逻辑；字段改名/新增后旧档只能“缺字段用默认值”。
- JSON 解析失败返回 `{}`，UI 可能把它当“空存档”，而不是“损坏”。
- 380 KB/次，`map_baked` 占 92%；金币变动也触发写盘。
- 没有 checksum/backup；`tmp` 替换失败时有回退，但没有“上一份好档”。

**方案**

```text
SaveData v2
├─ header: { schema_version: 2, game_version, created_at, checksum }
├─ player: { health, max_health, coins, abilities }
├─ world:  { room, checkpoint, doors, switches, items, quests }
└─ map:    { visited_rooms, reveal_mask_png, baked_rooms(仅已访问) }
```

- `SaveCodec` 负责 `to_dict/from_dict/validate/migrate`；`SaveManager` 只负责 I/O。
- 迁移链：`v1 -> v2 -> v3`，每步一个纯函数 + 单元测试。
- 校验：对 payload 做 SHA-256，写入 header；读档失败时尝试 `.bak`，再失败才提示“存档损坏”。
- 压缩：`FileAccess.open_compressed(..., FileAccess.WRITE, FileAccess.COMPRESSION_GZIP)` 或 zstd；实测 gzip 可到 53 KB。
- 增量：`map_baked` 只存 `visited_rooms`，或按房间增量更新；打开地图时再补烘焙。
- 写盘：全部走 `request_auto_save`；关键节点（Boss/章节）才强制同步写。

**评价指标**：存档大小（380 KB→<60 KB）、写盘 p95 耗时、损坏恢复成功率、迁移测试覆盖率。

**难度**：2/5；1–2 周；低风险。适合作为“软件工程/数据可靠性”章节，不是主线但很加分。

### 4.8 模块 D1：程序化装饰与生物群系美化

**目标**：解决“美化游戏场景”的人力瓶颈，同时保持关卡可玩性。

**技术组合**

- **Poisson Disk Sampling（Bridson）**：在房间内均匀撒装饰点，避免聚簇；按生物群系配置密度/最小间距。
- **WFC / Wang Tiles**：给地形边缘、墙面、植被做变体，减少重复感；约束“不能覆盖碰撞体/不能挡住门/不能生成在危险区”。
- **规则约束**：每个装饰 prefab 有 `biome`、`allow_on_slope`、`min_distance_to_door`、`collision` 等元数据；生成前做 AABB/物理查询。
- **编辑器时生成**：输出到 `.tscn` 静态节点，不在运行时生成；支持“重新生成/锁定/手动微调”。

**评价指标**：美术摆放时间、装饰密度/多样性、碰撞冲突数、帧率影响、人工评分（1–5）。

**难度**：4/5；3–4 周；中风险（美术风格不可控）。建议只做“装饰层”，不碰平台/碰撞。

## 7. 如果游戏不作为毕设：作品集优先路线

### 7.1 先做内容，还是先重做架构？

**先做内容，架构只做“服务内容的最小工具化”。**

理由不是“架构不重要”，而是你当前的目标函数变了：

| 目标 | 最重要的指标 | 架构重做的收益 |
|---|---|---|
| 发到社交平台 / 求职作品 | 前 10 分钟好不好玩、完成度高不高、有没有辨识度 | 很低，玩家看不见 |
| 毕设 | 有没有可论证的算法/数据贡献、能不能复现实验 | 也低，重写架构很难量化 |
| 长期维护 | 加内容是否顺手、改坏了能不能发现 | 中等，但可以用小工具替代大重写 |

你现在的项目是“学习空洞骑士/蔚蓝”的产物，它的价值在**手感、关卡、美术、完成度**，不在“企业级架构”。强行重做 `Player`/`Global`/`MapManager` 的风险是：手感变了、进度停了、作品集没做完。

**正确顺序：**

1. 先做 8–12 个房间的 **vertical slice**（20–30 分钟完整流程）。
2. 拿给 5–10 个人玩，记录卡点、误解、流失点。
3. 针对“反复出现的作者痛点”做小工具，而不是重写系统。
4. 内容稳定后，再谈性能/架构/毕设。

### 7.2 作为“求职作品”的诚实评价

**能打的地方：**

- 手感参数非常细：土狼时间、跳跃缓冲、边缘修正、墙跳逃逸、冲刺转向、Hit Stop、相机观察偏移。
- 系统广度大：房间流式加载、地图/迷雾、存档、对话、任务标记、挑战/竞速、成就、移动端 HUD、三语、按键重映射。
- 美术有辨识度：暖色像素风、角色可爱、标题卡有记忆点。
- 文档/复盘意识强：`Manals/` 里的房间手册、UI 过渡计划、Bug 复盘，面试时是加分项。

**玩家/面试官会立刻注意到的问题：**

1. **前 30 分钟没有“必须玩下去”的钩子**：能力很多（9 个），但没有一个被反复强化成“这游戏的招牌”。作品集需要一个 15 秒就能看懂的机制。
2. **内容密度不足**：63 个房间里有 22 个小于 10 KB；7 个金币；没有 Boss/高强度段落。广度有了，深度不够。
3. **教学依赖 NPC 对话**：`Master`/`AerialRollMaster` 直接授予能力，缺少“用关卡教玩家”的过程；玩家可能不知道怎么用。
4. **平台/发行准备不足**：`export_presets.cfg` 目前只有 Android；没有 Windows/Steam/itch 构建，也没有手柄映射。
5. **标题界面构图偏右重左轻**：主菜单贴右、标题卡在左上、中间大片空；主次按钮层级差距过大。
6. **仓库不像“作品集仓库”**：`android/build` 1.04 GB、630 个构建文件被 Git 跟踪，clone 很吓人；`.gitignore` 只有 3 行。
7. **缺少“可展示的证据”**：没有 trailer、GIF、press kit、devlog；招聘方不会自己跑 63 个房间。

### 7.3 作品集优先级（P0 → P3）

| 优先级 | 做什么 | 为什么 | 验收标准 |
|---|---|---|---|
| **P0** | 8–12 房间 vertical slice：出生 → 第一个能力 → 一次挑战 → 一个高潮 → 结束 | 作品集需要“完整的一小段”，不是“很大的半成品” | 20–30 分钟可通关，无软锁 |
| **P0** | 教学关卡化：安全教学 → 强制使用 → 变式 → 组合 | 比 NPC 发能力更能展示设计能力 | 新玩家 5 分钟内会二段跳/冲刺 |
| **P0** | Windows 导出 + 手柄映射 + 暂停/设置/退出 | PC 作品集的基本盘 | 手柄即插即用，Alt+F4 前能存档 |
| **P1** | 5–10 人 playtest + 录屏 | 发现“作者看不见”的问题 | 记录前 3 个卡点并修掉 |
| **P1** | 美术/音频统一：16px 网格、视差、粒子、BGM 混音 | 作品集第一眼是画面 | 截图/ trailer 不糊、不刺眼 |
| **P1** | 地图可读性：房间名、图标、迷雾、当前目标 | 类银河恶魔城的地图是核心体验 | 玩家能自己找到下一目标 |
| **P2** | 1 个挑战 + 1 个“高潮段落”（追逐/逃脱/极限跳跃） | 给 demo 一个记忆点 | 可在 30 秒内展示 |
| **P2** | 存档压缩/加载优化 | 移动端体验 | 存档 <60 KB，切图不卡 |
| **P3** | 发布：itch.io demo、trailer、devlog、press kit | 让作品被看见 | 有链接、有下载、有反馈 |

### 7.4 现在值得做的“小工具”（不是架构重做）

- **房间模板/检查清单**：新房间一键复制标准容器（Bounds、TileMapLayers、Doors、Checkpoints、Props、Audio），避免漏东西。
- **只读房间/门校验器**：扫描 `door_id/target_room_id/adjacent_rooms`，输出“未同步”列表；这就是 A1 的最小版本，做关卡时立刻省时间。
- **房间预览/截图工具**：批量给每个房间截一张图，做关卡索引和 trailer 素材。
- **Smoke test**：headless 打开每个房间，检查门配对、玩家出生点、缺失资源；比手动点 63 个房间快。
- **构建脚本**：Windows + Android 一键导出，版本号/图标/包名统一。

### 7.5 现在不要做的“架构重做”

- 不要把 `Player.gd` 改成 ECS / 行为树 / 全事件驱动；手感是资产，重写风险极高。
- 不要为了“软件工程感”引入 DI 容器、数据库、微服务、消息队列；单机游戏不需要。
- 不要重做 `MapManager`/`RoomManager`；它们已经在工作，重构收益远小于做内容。
- 不要全项目 `gdformat`；36k 行的 diff 会让你无法 review。
- 不要在没有 profile 的情况下优化性能；先测目标设备。
